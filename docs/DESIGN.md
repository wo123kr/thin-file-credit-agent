# 설계 — AI 피처 탐색 에이전트로 이력이 얇은 고객의 승인율 올리기

## 묻는 것

최근 이력이 얇은 고객은 지금 보이는 정보만으로는 점수가 잘 갈리지 않는다. 이력에서 피처를 더 뽑으면 **연체율을 그대로 두고 승인율을 몇 %p 올릴 수 있나**. 그리고 LLM 에이전트가 피처를 제안하고 코드가 검증하는 방식이, 사람이 만든 피처 위에 무엇을 더하나.

## 데이터

UCI 「Default of Credit Card Clients」(대만 은행 신용카드 고객 30,000명, CC BY 4.0). 2005년 4~9월 6개월의 상환 상태 · 청구액 · 납부액, 라벨은 10월 연체 여부(22.1%).

처음엔 Home Credit(Kaggle)을 쓰려 했으나, 대회 규칙의 특별 조항이 데이터 사용을 「대회 목적」으로 제한해 포트폴리오 공개와 맞지 않아 바꿨다(2026-11-02 사용자 결정).

**얇은 이력** = 6개월 중 청구액이 있던 달이 3달 이하인 고객. 3,779명(12.6%), 그중 연체 893명(23.6%). 모형 결과를 보기 전에 인원 비율만 보고 정했다.

## 분석용 DB (에이전트가 보는 것)

DuckDB 파일 하나, 읽기 전용으로 연다.

| 표 | 내용 |
|---|---|
| `clients` | 고객 1명 = 1행: `id`, `limit_bal`(한도), `education`(학력 코드) |
| `monthly` | 고객 × 달 = 1행: `id`, `month`(1 = 9월 … 6 = 4월), `status`(상환 상태), `bill`(청구액), `paid`(그 달 낸 금액) |

라벨(`is_default`)과 보호 속성(성별 · 혼인 · 나이)은 이 DB 에 넣지 않고 따로 둔다. 사후 공정성 점검에만 쓴다.

## 모형 사다리

모두 같은 모형(그래디언트 부스팅, 같은 설정)으로 피처 묶음 차이만 본다.

- **A 지금 한 장**: 한도, 학력, 이번 달(9월) 상환 상태 · 청구액 · 납부액. 심사 시점에 바로 보이는 정보.
- **B 사람이 만든 이력 피처**: A + 6개월 집계(연체한 달 수 · 최장 연체, 한도 소진율 평균 · 최고, 청구 대비 납부 비율, 청구가 있는데 0원 낸 달 수, 청구액 추세, 미사용 달 수). `tw-credit-scorecard` 의 피처를 그대로 옮김.
- **B + 에이전트**: B + 에이전트가 제안해 검증을 통과한 피처.

## 에이전트가 할 수 있는 것과 없는 것

- 할 수 있는 것: 데이터 설명 · 지금 피처 목록 · 지난 제안의 결과를 보고 피처 가설(한국어)과 DuckDB SQL 을 낸다. 한 제안에 1~3개 열.
- 할 수 없는 것: 라벨 · 보호 속성 보기(DB 에 없음), 파일 · 네트워크 접근(읽기 전용 DB, 외부 접근 끔), SELECT 가 아닌 문장, 시험 데이터 성적 보기.
- 채택 · 기각은 코드가 정한다. LLM 은 숫자를 정하지 않는다.

## 검증과 채택 기준

- 나누기: 개발 80% / 시험 20%(라벨 층화, 고정 시드). 시험 데이터 성적은 마지막에 **한 번만** 연다(두 번째 실행은 막는다).
- 제안 하나 검증: 개발 데이터 5겹 교차 검증을 3번 다르게 나눠(15쌍), 지금 피처 묶음 대비 「얇은 이력 고객 AUC」가 오르는지 같은 겹끼리 비교.
- 채택: 평균 ΔAUC(얇은 이력) ≥ +0.002 이면서 15쌍 중 70% 이상 양수, 전체 고객 AUC 는 -0.001 보다 나빠지지 않음.
- 기준을 바꾼 기록: 처음 이 문서에는 「5겹, 5겹 중 4겹 이상」으로 적었다. 에이전트를 처음 돌리기 전에 개발 데이터로 A · B 교차 검증만 돌려 보니 얇은 이력 AUC 가 겹마다 0.64~0.73 으로 흔들려, 겹 하나의 우연을 줄이려고 「5겹 × 3번, 15쌍 중 70%」로 바꿨다. 코드(model.py · agent/evaluate.py)는 첫 에이전트 실행 전에 바뀌었고 이 문서는 늦게 고쳤다(2026-11-02, 검토 지적). 에이전트 결과를 보고 바꾼 것은 없다.
- 기각: SQL 오류 · 시간 초과(30초) · 출력 모양 위반(고객 1명 1행, 숫자 열 1~3개) · 결측 95% 초과 · 단일 피처 AUC 0.85 초과(누수 의심) · 이미 있는 피처와 상관 0.98 초과.
- 모든 제안을 「가설 → SQL → 수치 → 결정 → 이유」로 `agent_runs/` 에 남긴다.

## 실험 2 (2026-11-02 추가, 시험 데이터를 열기 전에 정함)

실험 1(B 위에서 시작)에서 16개 제안이 모두 기각됐다(가장 큰 ΔAUC +0.0018). 채택 기준은 바꾸지 않는다. 대신 에이전트 혼자의 실력을 따로 잰다.

- **A + 에이전트**: 사람이 만든 이력 피처(B) 없이 A 에서 시작해 같은 규칙 · 같은 기준으로 4라운드 × 4제안.
- 비교: 시험 데이터에서 A + 에이전트 vs B(사람). 에이전트가 사람의 피처 설계를 얼마나 따라잡는지.
- 프롬프트의 「지금 모형이 쓰는 피처」에는 A 만 보인다. B 의 SQL 이나 이름은 주지 않는다.

## 결과 지표 (시험 데이터)

- AUC · KS(전체 · 얇은 이력)
- **같은 연체율에서의 승인율(얇은 이력)**: A 가 얇은 이력 고객의 50 · 70 · 90%를 승인할 때의 승인자 연체율을 기준으로, B · B+에이전트가 그 연체율을 넘지 않고 승인할 수 있는 최대 비율. 부트스트랩 1,000번으로 차이의 95% 구간.
- 사후 공정성: 성별 · 나이대별 승인율과 승인자 연체율.

## 범위 밖

- 비금융 대안 데이터: 이 데이터에는 없다. 그래서 질문은 「대안 데이터」가 아니라 「얇은 이력에서 이력을 얼마나 더 잘 읽나」다.
- 거래 순서를 직접 학습하는 순서 모형(GRU 등): 시간이 남으면 다음 단계로.
- 다른 시기 검증(OOT) · 거절자 결과 추정(reject inference): 한 시점 · 승인된 고객만 있는 데이터라 못 한다.
- 운영 배포 · 공개. 저장소 공개는 사람이 정한다.
